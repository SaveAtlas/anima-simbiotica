Consent challenge & fresh_required (S3.1)

Companions: EVENT-AND-CONSENT.md, ACTION-CLASSES.md, THIRD-SLICE.md
Rule: High-stakes acts need a fresh affirmation — not a stale grant alone.

1. When

If ConsentGrant has fresh_required: true, or action_class is in:

  • robot.act.low, robot.act.high
  • habitat.act.reversible, habitat.irreversible.* (latter usually forbidden for guardians)
  • federate.mesh.job, commerce.mesh.pay

…then before act, runtime must see a recent successful consent.challenge response bound to that grant.

2. Wire

challenge request (event)

{
  "kind": "consent.challenge",
  "emitter": "did:key:z...Node",
  "subject": "did:key:z...Being",
  "payload": {
    "grant_id": "grant-...",
    "action_class": "robot.act.high",
    "nonce": "hex",
    "prompt": "Allow high-stakes act?"
  },
  "sig": "..."
}

challenge response (event)

{
  "kind": "consent.challenge.response",
  "payload": {
    "grant_id": "grant-...",
    "nonce": "hex",
    "decision": "allow | deny",
    "answered_at": "2026-09-05T04:00:00Z"
  },
  "sig": "..."
}

Signed by Being (or Guardian in scope), not merely the Node.

3. Freshness window

v0 default: response valid for 5 minutes (configurable per grant later). Replay nonce → deny.

4. Builder sketch

  • Offline demo: python3 -m refnode challenge-demo auto-answers allow once, then act; second act without new challenge → deny.
  • Fail closed if response missing/expired/wrong nonce.
