ADR-001 — Separate BeingId and NodeId key material

  • Status: Accepted; reference-node migrated to distinct BeingId/NodeId keys + NodeBinding
  • Date: 2026-09-04
  • Deciders: Anima Architect (Ovie veto after review)

Context

Reference-node v0 roots BeingId and NodeId in the same ed25519 key (did:key + #node-… fragment). That is fine for an offline demo. It is wrong as a lasting model:

  • A being may have many nodes (phone, home, robot, habitat).
  • Compromising a device must not equal compromising the being’s root.
  • Exit and guardianship need clear “who” vs “where.”

Decision

  1. BeingId — long-lived DID controlled by the being (or guardian root).
  2. NodeId — distinct keypair per runtime place, bound to BeingId via a signed NodeBinding attestation (VC-shaped or simple signed JSON in v0.2).
  3. Rotation: revoke NodeBinding without rotating BeingId.
  4. Reference-node must migrate before any multi-device or networked federation demo.

Consequences

  • Slightly more setup UX (two key classes).
  • Enables real device loss / theft story.
  • Aligns with DIDs + VCs reuse map.
  • Reference-node holds distinct PEMs + signed NodeBinding JSON. Architect may still harden NodeBinding schema beside EVENT-AND-CONSENT; rotation UX later.

Non-goals

  • Mandatory hardware secure element in v0.2 (nice later).
  • Vendor KMS as root (adapter only).
